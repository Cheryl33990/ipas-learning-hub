# Chunking 與 embedding 的測試與選型

選型應回答「在我們的文件、問題與硬體限制下，哪個方案值得採用」，而非挑公開排行榜第一名。先測切塊是否正確，再量檢索品質與成本，最後才用固定生成模型驗證回答是否改善。本專案新增獨立的 [retrieval_eval.py](../src/ipas_hub/retrieval_eval.py) 與 [實驗設定](../examples/ipas/eval/retrieval-plan.json)；它不寫入正式資料庫、不更換服務模型。

## 1．先準備可信的問題與證據

每題需要查詢、來源版本及可接受的證據位置。**官方選項答案不足以評估檢索**：LLM 可能憑既有知識答對；「同科教材有出現」也不代表找到了正確依據。

建議人工標註時同時保存來源、PDF 頁序、書面頁碼與支持該問題的原文範圍，另記是否需要跨段／跨頁結合。把「可以支持回答」與「只提到同一個詞」分開；無解答的教材練習題不能直接當作正確說明。若有多個等價證據位置，均記錄；未審查的候選不能默認為不相關。

資料至少涵蓋術語精確查詢、同義改寫、中文混英文、長情境問題、跨段資訊，以及教材沒有答案的問題。先依題型與主題分開發集和最終測試集，同題改寫及共用情境要放在同一側。開發集可反覆看錯例；最終測試集要在候選方案凍結後才使用。若看了測試結果再調參，那批題目就不能繼續宣稱為未見測試集。

本輪使用歷史 **8 題開發案例**，保留原始參考頁，標為 `ai-provisional`。它們曾用於開發，頁碼標註有不完整與歷史爭議，且只有初級問題；檢索語料則是目前五科教材。這批只用來驗證流程與觀察差異，不作正式最優模型的證據。既有 243／248 題保留題評估維持原紀錄，沒有拿來替這次選型背書。

## 2．Chunking 分兩層驗證

| 層次 | 檢查內容 | 本輪做法 |
|---|---|---|
| 工程正確性 | 文字是否完整覆蓋、頁碼是否正確、重疊是否符合設定、不跨頁、末段不遺漏 | 四種視窗用合成頁測邊界與覆蓋；沿用既有 PDF／勘誤／雜湊測試 |
| 檢索效果 | 相關證據是否進前 k、是否被切斷、同頁重複是否排擠其他證據、上下文成本 | 頁面 Hit／Recall／MRR、重複頁比例、取回字元數；2026-11-19 起另算證據原文覆蓋（見下方第二輪） |

不要只測「有產生 chunks」或「能建向量」。即使工程測試全過，切法仍可能找不到證據。頁面命中也可能取回同頁中不支持問題的另一段，所以它是檢索代理指標，不能當語意支持率。

本輪四個候選都沿用目前的**頁內字元視窗**：

| ID | 大小／步長 | 完整相鄰視窗重疊 | 比較目的 |
|---|---|---|---|
| c200-s150 | 200／150 字元 | 50（25%） | 較細片段是否提升定位，或失去上下文 |
| c400-s400 | 400／400 字元 | 0 | 與 400／300 比較，隔離 overlap 的影響 |
| c400-s300 | 400／300 字元 | 100（25%） | 現行基線 |
| c800-s600 | 800／600 字元 | 200（25%） | 較大片段是否改善上下文，但增加截斷／成本 |

200、400、800 比較維持相同重疊比例；400 的兩組只改重疊。這是事前選定的有限探索範圍，沒有聲稱涵蓋最佳值，也尚未比較段落、章節或語意切塊。

## 3．Embedding 要依各模型正確的輸入契約比較

固定同一份文件、解析／勘誤版本、切塊、問題、正規化、檢索方法與 k，再換 embedding。使用各自要求的 query／document 前綴，不應為了「字串完全相同」而故意錯用模型。

| 候選 | 本輪用途 | 使用方式 |
|---|---|---|
| BAAI/bge-m3 | 目前模型，作基線 | dense 向量、1,024 維、CPU、文件／問題都正規化，無額外前綴 |
| intfloat/multilingual-e5-small | 探索較小模型是否能降低本機成本 | dense 向量、384 維、CPU、正規化；問題加 `query: `，文件加 `passage: ` |

兩者固定 snapshot commit，見實驗設定。E5 官方要求非英文查詢也加前綴，並限制最多 512 tokens；因此工具量測文件與問題的原始 token 數，記錄實際 `max_seq_length` 與超限數，不能把字元數直接當成 token 數。[E5 官方模型卡](https://huggingface.co/intfloat/multilingual-e5-small)；BGE-M3 的多種輸出模式中，本輪只測 dense，[官方模型卡](https://huggingface.co/BAAI/bge-m3)。

本輪執行四組切塊 × 兩模型完整交叉比較，觀察模型與切法的交互影響；每種切塊另跑 BM25 控制組。每個 embedding 分別跑向量與混合檢索，沿用正式 `KnowledgeBase.search` 的排序與 RRF（各前 20、常數 60），不另寫一套較有利的排序。BM25 每個切法只算一次，共 20 個比較單元。

這輪使用檔案索引及記憶體向量矩陣，不查詢 PostgreSQL；延遲反映這個離線路徑，不能直接與既有 pgvector／聊天端點或舊評估的毫秒數比較。資料庫效能不是本輪變因。

實驗的 E5 前綴 adapter 僅在 evaluator 使用。正式 `local_encoder`／索引契約目前沒有此設定，**不能把實驗向量直接搬去正式 serve 使用**；若之後選定 E5，仍須實作、測試及版本化正式輸入契約後重建索引。

## 4．指標如何讀，哪些還沒測？

工具回報 k=1、3、5，k 的單位是**片段**。頁面用 `(source, page)` 識別，避免不同文件同頁碼混算；計算命中與召回時去重，但不移除原始排名中的重複片段。

每次實際搜尋取最大 k（本輪 5），再取排名前綴計算 k=1、3、5 指標；三列共用這次搜尋的延遲，並非三種 k 各自重新計時。

| 指標 | 定義／解讀 |
|---|---|
| Hit@k | 前 k 片段至少包含一個參考頁的題目比例 |
| Page Recall@k | 每題命中的不重複參考頁數／標註參考頁總數，再對題目平均；標註不完整時只是對已列參考頁的召回 |
| MRR@k | 第一個參考頁出現在第 r 個片段時得 1/r，沒命中得 0；同頁重複仍消耗名次 |
| 重複頁比例 | `1 − 不重複頁數／取回片段數`；不是文字重複率，也不表示同頁多段一定無用 |
| 上下文字元數 | 前 k 片段文字長度總和；重疊照計，反映實際上下文負擔 |
| p50／p95 | 暖機後每次查詢耗時，向量／混合包含問題嵌入；不含載入模型、生成與逐句核對 |
| 建置成本 | PDF 解析／切塊時間、文件嵌入時間、片段數、向量維度與向量 raw bytes 分開記；raw bytes 不等於完整 DB／模型 RAM |
| token 截斷 | 文件與問題超過 encoder 上限的數量；被截斷的證據可能影響排名 |

已知無答案題（`expected: []`）排除 Hit／Recall／MRR 分母，另報是否仍回傳候選。**回傳候選不是錯誤回答，也不是拒答率**；本工具沒有呼叫生成模型。未標註問題不能填空陣列假裝無答案。

若問題要結合兩頁，Hit 只找到一頁也會算成功；若兩頁是等價的替代依據，則不一定需要全部找齊。`expected` 是平面的相關頁集合，沒有表達「任一組即可／同組必須齊全」，所以 Recall 不能直接當回答充分率。2026-11-19 起案例可另加 `evidence`：每個 requirement 都必須滿足（必須合併），其下 alternatives 互為等價替代；每個 alternative 記來源、頁、逐字引文與判定（direct／partial／unsupported／uncertain），只有 direct 計分。工具從片段序號與步長還原頁內位置：取回片段的聯集蓋住某段 direct 引文才算滿足（complete）；單一片段就完整包含才算未被切斷（intact）。引文必須逐字存在於解析頁，否則拒絕執行。有人工相關性等級後才適合再加 nDCG 等分級指標，不先用 AI 猜分當 ground truth。

固定 k 不能保證固定上下文成本：五個 800 字元片段最多比五個 400 字元片段多一倍文字。因此即使大塊 Hit 較高，也不能直接稱效率較佳；正式決策還應補相同生成模型 tokenizer 下的固定 context token budget 比較，以及人工對照實際取回片段的證據支持度。2026-11-19 起計畫可設 `budgets`（字元）：依排名累加片段，超過預算即停止，所以 800 字元片段在 2,000 字元預算下只取 2 個、200 字元片段取 10 個。這是字元近似，仍不是生成模型 token budget。工具也保存每題前 20 名片段 id，日後換標註可直接重評。

未量測峰值 RAM、磁碟總占用、併發吞吐、GPU embedding、ANN 或 reranker；不從向量檔大小推算它們。排名以一次完整查詢計分；其餘重複執行用於延遲與排名穩定性，不能將 8 題 × 3 次當成 24 個獨立樣本。方法與模型採固定執行順序，服務仍在同一台電腦運作，延遲只供探索，不當嚴格效能排名。

## 5．在本專案重跑

需要 `uv sync --locked --extra embeddings`、來源設定所列 PDF／勘誤及本機模型快取。來源雜湊必須一致，缺勘誤不應偷偷略過；若改用無勘誤設定，須另開實驗並保留差異。

1. 建立本機案例 JSON，放在 `data/evaluation/`。最小格式如下；示意題需換成實際問題與人工核對的頁碼，不能用它產生品質結論。

   ```json
   {
     "split": "development",
     "label_status": "ai-provisional",
     "cases": [
       {
         "id": "example-01",
         "query": "待替換的示意問題",
         "expected": [{"source": "subject1", "page": "3-1"}]
       }
     ]
   }
   ```

   人工審查後另存新版，改成 `human-reviewed` 並附 `review_record`，不要覆蓋舊標註。`split: test` 要求人工審查標記，但工具無法查證人是否真的審過或資料是否真的未曾用於開發；仍需保留抽樣、隔離與確認紀錄。

2. 下載固定版本（只有首次需要連網；權重不進版控）：

   ```powershell
   uv run --no-sync hf download BAAI/bge-m3 --revision 5617a9f61b028005a4858fdac845db406aefb181 --exclude 'onnx/*' --exclude 'openvino/*' --exclude 'imgs/*' --exclude '*.jpg' --exclude '*.png' --exclude '*.webp' --exclude '*.pt' --exclude '.gitattributes'
   uv run --no-sync hf download intfloat/multilingual-e5-small --revision 614241f622f53c4eeff9890bdc4f31cfecc418b3 --cache-dir data/models/hub --exclude 'onnx/*' --exclude 'openvino/*' --exclude 'imgs/*' --exclude '*.jpg' --exclude '*.png' --exclude '*.webp' --exclude '*.pt' --exclude '.gitattributes'
   ```

3. 執行離線比較：

   ```powershell
   uv run --no-sync python -m ipas_hub.retrieval_eval --plan examples/ipas/eval/retrieval-plan.json --cases data/evaluation/retrieval-dev.json --out data/evaluation/retrieval-study-new
   ```

   只改標註或評分方式時，可加 `--reuse-vectors <舊輸出資料夾>` 沿用文件向量：工具逐一核對片段全文、模型 revision／前綴與記錄的向量雜湊，任一不符即拒絕，結果記 `vectors_reused_from`，文件嵌入時間記為空值而非 0。

   可用 `--model bge-m3 --chunk c400-s300` 先跑小範圍；報告會列已完成／全部單元數，不把部分結果當完整比較。重用同一輸出資料夾時，已完成的單元略過；若案例、設定、程式、lock、Python／套件版本或來源／勘誤雜湊不同會拒絕混算（2026-11-19 前的版本未把 Python／套件版本納入指紋），須另開資料夾。換硬體或執行環境也應另開資料夾，避免混入不同比較條件。

   完整矩陣需要八次文件嵌入建置；CPU 執行可能耗時數十分鐘，不能把它當成一分鐘 smoke test。建議先跑上述單一候選確認資料、前綴與報告，再執行完整矩陣。

4. 查看輸出的 `meta.json`、`report.md` 與每個切法下的結果 JSON。每筆保留參考頁排名、逐題指標、模型版本／前綴、資料與程式雜湊、時間與截斷統計。案例與索引含原文，只能留在 `data/`；對外報告只摘錄無原文的設定、數字與限制。

工具不下載模型、不呼叫生成 API，沒有模型就明確失敗。失敗前已完成的單元可保留，但須確認完整性後才能解讀整體比較。預設 CPU 4 threads、batch size 8，查詢暖機一次後每題重複 3 次；建置時間含首次嵌入成本，未冒稱冷啟動與暖啟動皆已測量。

下載與載入使用相同排除清單；不要只下載 safetensors 後就假設離線快取完整。新版 Hugging Face Hub 可能依 snapshot 清單要求其他附檔；若收到 `IncompleteSnapshotError`，以相同 revision 與上述排除清單補齊後再續跑，不能換成新版本或把失敗結果填為 0。

## 5a．開發集與新測試集安排（提案，待作者確認）

| 集合 | 內容 | 可以怎麼用 |
|---|---|---|
| 開發集 | 既有 8 題（v1 頁碼與 2026-11-19 證據草稿）、既有 243／248 題中已分析過的錯例與拒答題，以及新寫的開發題 | 反覆看錯例、調整切法與標註規則；不可宣稱未見 |
| 回歸集 | 既有 243／248 題回答評估 | 確認改動沒有讓舊結果退步；已被分析，不可重新稱為全新保留集 |
| 新測試集 | 本輪之後才撰寫、尚未送進任何檢索或模型的題目；標註凍結並記錄雜湊後才第一次執行 | 候選方案凍結後只跑一次做最終比較；看了結果再調參，就降級為開發集 |

切分單位是**概念組**，不是單題：同一概念的原題、改寫、中英混合版與長情境版放在同一組，整組只能進開發集或測試集。每組依下列題型標記，兩個集合都要涵蓋：

| 題型 | 例子（示意） | 證據要求 |
|---|---|---|
| 術語精確 | 直接問「差分隱私」 | 單一需求、可有多個等價頁 |
| 改寫 | 不出現教材術語，只描述「加雜訊使單筆資料不影響結果」 | 同上；測 BM25 與向量差異 |
| 中英混合 | 「Self-Attention 為何能處理長距離依賴」 | 同上；測斷詞與 tokenizer |
| 長情境 | 試題式情境＋四個選項 | 可能需排除干擾選項的證據 |
| 跨段／跨頁 | 迴歸任務＋MAE 指標（初級無 MAE，需中級頁） | 多個需求必須全部滿足 |
| 無答案 | 教材 2025 版之後的新主題 | `expected: []`，另測拒答，不計入 Recall 分母 |

2026-11-19 作者同意先準備新測試集，配置草案見[新測試集 v1 規劃](internal/project/design/retrieval-test-set-v1.md)：30 組（術語 6、改寫 6、中英混合 5、長情境 5、跨段 4、無答案 4），題目由作者撰寫，並排除 8 題開發集的概念。規模先以每型至少數組、總計約 30 組為起點，這是工作量估計，不是統計門檻；樣本小時報逐題改善／退步與成對差異區間，不只報平均。標註流程：AI 依全庫關鍵詞與候選池起草 → 作者判讀「直接／部分／不支持／不確定」與需求組合 → 另存 `human-reviewed` 版本並附 `review_record`。測試題由作者或非開發者撰寫較佳；AI 撰寫的題目要註明，避免同一 AI 同時出題、標註與調參。

## 6．什麼時候才應改正式設定？

目前沒有已確認的品質或延遲門檻，因此本輪不自訂「提高 5% 就通過」。先看開發集逐題改善／退步與資源取捨，尤其要人工看：命中是否只是同頁不同段、較小片段是否失去限制條件、較大模型的收益是否值得成本。

候選方案凍結後，再用獨立且人工確認的測試集比較；報告樣本數與成對差異的不確定性，不只挑最高平均分。接著固定生成模型、prompt、外搜政策與上下文 token budget，重跑回答及引用支持度，確認檢索代理指標的改善有轉為使用者可感受到的好處。工程測試、檢索測試、回答測試各自過關，才由作者決定是否採用並重建正式索引。

這是分階段工作：本輪先交付可執行工具與探索結果；人工 gold、未見測試題、固定 token budget 的完整回答驗證仍是後續工作，沒有被文件完成取代。

|---|---|---|---|
