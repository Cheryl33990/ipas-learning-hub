# 雙科 RAG 原型與 Docker 執行契約

範圍與授權見 [brief](../brief.md) 的下一輪；實際驗證見 [progress](../progress.md)。本輪是自用技術原型，先提供 CLI，未交付網頁介面或部署服務。

## 執行與資料邊界

`index → search → ask → evaluate` 分開執行。來源只由 config/knowledge-base.json 明列的兩份教材建立，不讀試題與現有完整解析。原始教材、勘誤替換字串、索引、模型與查詢紀錄均不進映像／Git／CI。Docker Compose 把原始 PDF 掛唯讀，索引與執行紀錄存本機 data/；LLM 是可選 profile，模型需明確指定並另行下載，不自動選型。

使用者本輪進一步選擇「先完成檢索，下一步再選 LLM」。Ollama adapter 與 llm profile 僅為可替換的連接草案，本輪未選定 LLM、未啟動模型服務。小型雙科語料先沿用 BM25 與 NumPy 本機向量，不增加資料庫服務。向量檢索用本機已快取的 BAAI/bge-m3，固定 snapshot revision，未快取即失敗；不在查詢時下載新模型。混合檢索以兩路排名融合為原型候選，不宣稱優於單一路徑。向量方法無適用的品質閾值，仍可能回傳不相關片段，需用評估與人工內容審查判定。

## 可追溯性與回復

每個索引保存資料 schema、來源 PDF 與勘誤雜湊、實際套用頁、切塊設定、程式 commit／檔案雜湊、uv.lock 雜湊與 embedding revision／向量雜湊；整體內容雜湊是 index_id。新索引另建目錄，舊索引保留，查詢指定 index.json 即可回復版本。執行紀錄保存問題、片段、方法、索引識別、prompt 雜湊與延遲，只寫 data/runs/。這是 MLOps 的最小追蹤基礎，尚無模型註冊／漂移監控平台。

## 生成 prompt 契約（原型 v0.1）

- 實際 prompt：src/ipas_hub/prompts/answer.txt，程式以內容 SHA-256 追蹤。依據為已確認的下一輪方向及原先「程式檢查不等於理由正確」的限制，未虛構已採用的產品 AC。
- 輸入：JSON 的 question 字串與 evidence 陣列；每個片段含 id、source、name、version、page、text、rank、index_id。
- 輸出：JSON 的 status（supported／insufficient）、answer（繁體中文，包含選項時逐項解釋並區分推論）、citations（提供片段 ID 的陣列）。
- 正例：合成來源 s2:3-1:0 支持問題概念時，answer 引用該 ID，citations 亦列該 ID。
- 反例：無 evidence 時不呼叫模型；模型引用不存在的 ID，或聲稱 supported 卻沒有引用，程式拒絕該回答。
- 已知失敗：引用 ID 正確但文字仍可能不被片段支持；局部引用不能證明整段理由；模型可能遵從題目／教材中的惡意指令或把自身記憶冒充依據。prompt 只作約束，不把它當作已解決這些風險。需要人工或另外的語意驗證。
- 本機模型呼叫：Ollama /api/generate，JSON、非串流、temperature=0；僅允許 localhost、127.0.0.1 或 Compose ollama，不提供雲端 API 金鑰參數。模型連線、載入、逾時或輸出格式失敗明確回報，不退回編造答案。（v0.1 歷史描述；2026-11-17 起由下節 v0.2 取代）

## 生成契約 v0.2：教材＋外部搜尋（2026-11-17）

依 brief 第四輪的使用者決定實作；取代 v0.1 的 Ollama 介面。

- 流程：教材檢索前 k 塊 → 模型規劃最多 3 個搜尋詞（prompts/web_queries.txt）→ 每個詞輪流取外部結果，上限 --web-k → 模型依 prompts/answer.txt 回答。
- LLM 介面（src/ipas_hub/llm.py）：OpenAI 相容 /chat/completions，temperature=0、JSON 輸出。預設只允許 localhost、127.0.0.1 與 Compose 的 vllm；遠端端點須 --allow-remote 且為 https。金鑰只讀 LLM_API_KEY，執行紀錄只記端點與模型名。回覆被截斷、非 JSON、連線失敗都明確報錯。
- 外部搜尋（src/ipas_hub/websearch.py）：統一欄位 id、source_type、provider、title、url、revision、text、retrieved_at、query。維基百科以 zh-TW 取繁體，網址以 curid＋oldid 固定版本；429 依 Retry-After 等待後只重試一次（上限 5 秒）。搜尋失敗不中止，記在執行紀錄的 web.error，只用教材回答。
- 輸入：evidence 每筆含 id、source_type（textbook／external）、label、text，外部另含 url。
- 輸出：status、answer、citations。程式依片段資料加上 sources（逐筆標教材或外部）與 basis（textbook_only／external_only／mixed／none），不採信模型自稱的來源。
- 拒絕規則：引用不存在的 id、supported 卻無引用、格式不符時，把問題回饋模型修正一次；仍不合格即拒絕。教材與外部 id 重複時拒絕。無任何依據時不呼叫模型。
- 已知失敗（實測見 progress 第四十一筆）：引用 id 存在但內容不支持該句，例如第 28 題首次執行把 MAE 掛在沒有 MAE 的教材塊上；模型可能把引用集中放在答案末尾，讀者無法分辨哪句來自教材、哪句來自外部；外部搜尋可能回傳無關條目；模型可能用自身記憶作答或說得過度肯定。這些需要人工或另外的語意檢查。

## 生成契約 v0.3：逐句引用與字詞核對（2026-11-17）

使用者同意 AI 建議的下一步「引用逐句標示＋簡單內容核對」；取代 v0.2 的輸出格式，其餘流程（檢索、搜尋詞規劃、外部搜尋、修正一次）不變。

- 目的：讀者能看出每一句來自教材還是外部；明顯掛錯的引用（如句中的 MAE 不在被引用片段內）要被標出來。不是語意驗證。
- 模型輸出：`{"status", "segments": [{"text", "citations": [id]}]}`。每個 segment 是一個論點或一句；推論、結論（如「答案：B」）可不引用。
- 結構檢查（不合格修正一次，仍錯即拒絕）：segments 須為非空清單、text 非空、citations 為字串清單且 id 存在；supported 時至少一個 segment 有引用。
- 字詞核對（只標示，不拒絕）：對每個有引用的 segment，比對被引用片段的合併文字：
  1. 關鍵詞：句中的英文詞（2 字元以上，不分大小寫）與數字，若都不出現在被引用片段，列為 missing_terms。
  2. 中文重疊：句中連續中文的字元二元組，有多少比例出現在被引用片段，記為 overlap。
  3. missing_terms 非空，或 overlap 低於 0.1，標為「可能不支持」。0.1 為暫定：首次實跑 6 題中 17 句帶引用的句子，合理改寫與掛錯的句子重疊都在 0.14–0.58，原試用門檻 0.3 標出一半以上且分不開對錯，因此只留近乎無交集的極端情況，主要依英文詞／數字缺漏（見 progress 第四十五筆）。不當作品質門檻。
- 依據不足：status 為 insufficient 且 segments 為空時接受，由程式補一句「資料不足以判定」；supported 時 segments 不可為空。
- 顯示：每句後接程式產生的標記，教材為 [教材n]、外部為 [外部n]，依首次出現編號；被標記的句子下一行加 ⚠ 與原因；依據清單用相同標記。結果仍保留 answer 字串、citations、sources、basis，另加 segments 與核對結果。
- 測法：合成測試（假 LLM）涵蓋逐句標記與編號、未引用句、關鍵詞缺漏、重疊低、結構錯誤的修正與拒絕、模型在 text 內自己寫的 [id] 被清掉；實機以 vLLM 跑 3–5 題（含第 28 題與 8 題以外的題目），記錄每句引用與被標記句，人工抽看被標記與未被標記各幾句，誠實列出誤標與漏標。
- 已知限制：同義改寫會讓重疊偏低而誤標；片段含相同字詞但意思相反時不會被標出；未引用的句子不檢查。

## 外部搜尋 v0.4：前後文與英文維基備援（2026-11-17）

使用者提出「用前後文判斷」同名詞，並接受引進英文來源；取代 v0.2 外部搜尋的單一中文搜尋詞做法，生成契約 v0.3 不變。

- 搜尋詞規劃：每個概念給 zh、en；只有縮寫、英文術語或多義詞才加 domain_zh／domain_en（領域詞）。搜尋時概念詞＋領域詞一起送出，相關性與段落只依概念詞判斷。
- 相關性：概念詞的每個詞都要出現在標題或內文。英文須是完整的字（LIME 不配 timeline）；中文至少一半的字元二元組出現（暫定）。有領域詞時，導言或所取段落也須出現領域詞。消歧義頁一律排除。
- 段落：導言不含概念詞時，抓該頁全文，取含最多概念詞的段落（每次搜尋最多再抓 2 頁）；仍找不到就捨棄。
- 備援：中文維基沒有相關結果，或中文維基出錯時，改查英文維基；英文加領域詞查不到，再只用概念詞查一次。中文不重試無領域詞的查詢，因為同名無關條目多半出在那裡。英文結果 id 為 wiki-en:頁碼，標為「外部 英文維基百科」。
- 請求：同一來源兩次請求至少間隔 0.5 秒；單一搜尋詞失敗只記在 web.error 並略過，不影響其他詞。
- 字詞核對調整：所引片段沒有中文（如英文維基）時，不算中文重疊，只檢查英文詞。
- 未採用：以 bge-m3 計算結果與題目的相似度來篩選。實測每題多約 19 秒載入、3 秒計算，且有用條目（平均絕對誤差 0.52）與掛錯條目（RANSAC 0.54）分數交錯。
- 已知限制：中文二元組規則仍會放過部分無關頁（如「k-匿名化」配到「匿名者（黑客組織）」）；請求變多後較易遇到 HTTP 429，本機連續實跑時曾發生；User-Agent 已附 repo 網址作為聯絡方式（使用者 2026-11-17 同意），是否因此減少 429 尚未驗證。

## 聊天介面端點 v0.5：OpenAI 相容 /v1/chat/completions（2026-11-17）

使用者選定 AnythingLLM（MIT）當介面；本專案以 `serve` 指令提供端點，平台把它當成一個模型。生成契約 v0.3 與外部搜尋 v0.4 不變。

- 介面：`python -m ipas_hub.cli serve --index <index.json> [--port 8100] [--served-name rag]`，參數與 `ask` 相同（--method、--k、--web、--web-k、--model、--llm-url）。只綁 127.0.0.1，不提供改綁選項。提供 GET /v1/models 與 POST /v1/chat/completions（含 stream；回答一次產生，整段放在一個 chunk）。
- 輸入：取最後一則 role 為 user 的訊息當題目；平台附帶的系統提示、歷史對話與其他參數不使用，所以目前每題獨立、沒有多輪記憶。
- 輸出：`render_text` 的文字原樣回傳。流程重用 cli.ask() 與 rag.answer()（cli.answer_text），每次請求照樣寫 data/runs/。
- 失敗顯示：LLM 無法連線、模型輸出格式或引用不合格、索引讀取失敗等，以 HTTP 200 回一則以「⚠ 無法產生有依據的解答」開頭並附原因的訊息，讓聊天畫面直接顯示，不冒充解答。外部搜尋失敗（如維基 429）時仍回答，文末加「⚠ 外部搜尋未完整」。依據不足沿用 render_text 的「狀態：依據不足」。請求沒有使用者訊息或不是 JSON 時回 HTTP 400。
- 通用性：server.py 不含教材或考試專用邏輯，只接受一個「題目 → 文字」的函式；模型名稱預設為 rag。勘誤、頁碼等教材專屬處理仍在索引與 rag 模組內。
- 平台：compose.yaml 的 `ui` 服務（--profile ui），以環境變數把 LLM 指到 host.docker.internal 的端點。工作區不上傳文件，平台自己的檢索就不會介入；若上傳文件，平台會改用它內建的嵌入模型（需下載）並把片段塞進提示，本專案端點會忽略那些片段。
- 測法：合成測試（tests/test_server.py）涵蓋取題、分段內容、缺題回 400、成功格式、三種失敗顯示為警示、串流格式、實際 HTTP 來回（只綁迴路位址）、cli.answer_text 重用 ask／render 與搜尋失敗提示。實機以 vLLM＋AnythingLLM 跑少量題目，結果見 progress。
- 已知限制：沒有多輪對話；回答要等整段完成才顯示（3–22 秒）；引用仍只有章節頁碼；畫面上的排版（換行、⚠ 行）未經檢視；平台若另外送出產生標題之類的輔助請求，也會被當成題目執行。

## 引用定位 v0.6：PDF 頁碼與教材連結（2026-11-17）

使用者試用後要求引用補 PDF 頁碼並可連到教材該頁，並同意以下做法。生成契約 v0.3、外部搜尋 v0.4 不變；端點 v0.5 的輸出改為下述 Markdown 依據清單，取代其「引用仍只有章節頁碼」的限制。

- 索引：`read_pages()` 記錄每頁在 PDF 檔內的頁序（從 1 起算；封面、目錄等沒有頁尾頁碼的頁仍計入頁序但不建片段）。每個片段多一個 `pdf_page`，來源多一個 `pdf`（設定檔所列的相對路徑）。schema_version 維持 1：欄位只增不改，舊索引照常可讀。
- 送給模型的 evidence 不變（label 仍是「教材 名稱 章節頁碼」）；`pdf_page` 與來源識別只附在結果的 sources，供程式顯示。
- 顯示：教材引用為「教材 名稱 3-36（PDF 第 42 頁）」。`ask --format text` 只顯示頁碼；`serve` 的依據清單為 Markdown 連結，教材連到 `<link-base>/files/<來源識別>.pdf#page=N`，外部連到原網址。舊索引沒有 `pdf_page` 時只顯示章節頁碼、不產生連結。
- 檔案提供：`serve` 在同一個埠提供 `GET /files/<名稱>`。server.py 只接受呼叫端給的「名稱 → 路徑」允許清單並比對完整名稱，不把請求路徑接到檔案系統；沒有寫入方法。cli 只列入索引記錄、位於 data/ 且 SHA-256 與索引相同的教材；不符或缺檔時啟動訊息提醒，該來源不提供連結。
- 網址：連結是給使用者的瀏覽器開的，預設 `http://127.0.0.1:<port>`，與 AnythingLLM 容器連端點用的 host.docker.internal 無關；需要時以 `--link-base` 覆寫。
- 回復：新索引另存新目錄，舊索引目錄不動；`--index` 指回舊的 index.json 即回到只有章節頁碼的行為。
- 測法：合成測試涵蓋跳過無頁碼頁後的頁序、勘誤與切塊保留頁序、索引寫入與讀回、純文字／Markdown 兩種顯示、舊索引無連結、方括號跳脫、允許清單以外與路徑穿越回 404、雜湊不符不提供。實機重建索引並核對頁序，結果見 progress。
- 已知限制：`#page=N` 由瀏覽器內建 PDF 檢視器處理，其他檢視器可能不跳頁；只定位到頁、不標示段落；檔案整份傳送、不支援分段請求；serve 沒在執行時連結打不開。

## 生成契約 v0.3.1：明寫答案選項與核對註記（2026-11-17）

新題試跑（progress 第五十六筆）發現：8 題中 5 題沒寫「答案：X」；⚠ 多半由題目本身的英文詞觸發；模型把 id 寫在圓括號內，留在句中又被當成缺漏的詞。使用者同意先修再做 pgvector。只改以下幾點，v0.3 其餘規則不變。

- 答案選項：題目含兩個以上 (A)–(D) 選項標記即視為選擇題。prompt 要求最後一個 segment 為「答案：X」。結構合格但缺答案選項時，併入原本唯一一次的修正機會；修正後仍缺就照常顯示，加一行「⚠ 模型未明寫答案選項」，不拒絕。依據不足時不要求答案。結果新增 answer_choice、choice_expected。
- 字詞核對：缺漏的詞若出現在題目中，另列 question_terms，原因註明「題目中的詞（可能只是重述題目）」，仍算標記。不略過的理由：既有紀錄中掛錯的 MAE、K-means、SVC 都在題目內，Chunking 題被標的「AI」也是真的掛錯；略過會把這些一起藏起來。
- 句中 id：除了 [id]，（id）與 (id) 也移除；括號內不全是 evidence id 的保留。
- 測法：合成測試涵蓋缺答案時修正一次、修正後仍缺的註記、非選擇題與依據不足不要求、題目用詞的註記、圓括號 id 的清除。實機以相同 8 題重跑，結果見 progress。
- 已知限制：答案選項以字串比對讀取，模型寫成其他格式就讀不到；題目用詞的 ⚠ 數量沒有減少，只是說明來源。

## CI 與交付

CI 使用合成資料跑單元／流程測試、Compose config、Docker test stage 與 runtime --help，不把官方 PDF 或模型送到 hosted runner。手動 delivery workflow 只重建測試與 commit 標籤映像並記 image ID，不推送、不部署，尚不是生產 CD。Python 與 uv 基底映像已固定實際建置取得的 digest；vLLM 映像已以 digest 固定、模型以 revision 固定；hosted CI 不啟動模型。容器實測與真實 LLM 執行必須各有證據，不能從 YAML 存在推定通過。
