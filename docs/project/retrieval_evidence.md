# RAG 完整度與混合搜尋證據

目前定位：能展示教材下載、可追溯索引、混合檢索、PostgreSQL、生成、引用與聊天介面的本機原型。功能串接與工程檢查已有證據；新手獨立安裝、五科混合搜尋品質及多人服務能力仍未驗收。這不是正式產品完成度百分比。

## 完整度盤點

| 面向 | 已有證據 | 仍缺什麼 |

| 生成與引用 | 本機 vLLM、教材＋維基、引用檢查與拒答、教材 PDF 連結 | 理由與引用的語意正確性；字詞警告不等於事實查核 |

對外可用描述：「我們已完成可追溯引用的本機 RAG 原型。初步 14 題對照中，混合搜尋的答案選項一致數為 11 題，BM25 與向量各 10 題；差異小，尚待在現行五科索引上獨立評估。」

不支持的描述：「混合一定更準」「答對率已達穩定水準」「查詢只要 211 ms」「pgvector 讓回答更正確」。向量資料庫是儲存與距離計算選擇，不能單靠採用它證明品質；211 ms 是特定舊實驗的檢索中位數，不含完整回答。

## 下一輪評估方案（暫定，待採用，未執行）

先決定使用場景是自用還是給他人使用，再確認可接受延遲與判準。先量測基準，不事後選一個剛好通過的門檻。

1. 凍結程式 commit、五科 index_id、勘誤狀態、模型 revision、prompt、硬體、k 與 RRF 設定。現行 RRF 各取 BM25／向量前 20，累計 `1/(60+rank)`，預設回傳 5；不是分數直接相加。
2. 從五科與不同梯次選未用於調整的題目，分開列關鍵字明確、同義改寫、跨科、需推理與教材不足。題幹／選項、官方答案、人工依據分開保存；原測試題不放進檢索語料。教材自帶練習題／解答是否保留須預先決定並分層報告，避免洩漏。
3. 先盲審候選片段：隱藏方法、隨機順序，人工判核心支持／部分支持／不支持；保留未判定狀態，另人複核分歧。頁碼相同不代表片段足以支持答案。先選合理數量做標註試跑，再依各科錯誤與比較不確定性擴充，不硬編樣本門檻。
4. 同題比較 BM25、向量、混合，索引／查詢／k 完全一致。先關 web 看內部檢索差異；再用固定或快照外部證據做端到端比較。若即時維基改變，明寫混雜因素。調參集與最後保留測試集分開。
5. 品質至少報：前五有核心支持的題數／分母、首個核心片段排名、選項正確、理由正確、引用支持、合理拒答與錯誤拒答。只有單一目標頁命中率不是完整召回率；未完整標註相關集合時不宣稱 Recall@k。
6. 速度分開量：首次載入、暖機後問題嵌入、資料庫／BM25／融合、外部搜尋、LLM、完整回答。暖機後多輪、輪換方法順序，報 p50／p95、樣本數與硬體；單人與多人並行分開。CI 時間與建索引時間不當線上延遲。
7. 同題成對列出混合改善／退步／持平及失敗原因；報差異與不確定範圍，例如題目為單位的成對 bootstrap。若增益不確定，保留「未證實優勢」，評估多出的向量延遲是否值得。

## 現有工具可以先量什麼

CLI 的 evaluate 接受 `data/evaluation/` 內的 JSON 陣列，每筆有 id、query、expected（source、page 陣列）。它只計算前 k 結果是否命中任何預期頁、每題查詢延遲，不計完整支持、真正召回率、p95 或理由正確性；無依據題要另外人工評估。

先從資料庫取得並固定完整 index_id，在 PowerShell 設定 `$evaluationIndexId` 為實際識別，再執行：

```powershell
foreach ($method in @('bm25', 'vector', 'hybrid')) {
  uv run python -m ipas_hub.cli evaluate --store pg --index $evaluationIndexId --method $method --k 5 --cases data/evaluation/heldout_cases.json
}
```

`heldout_cases.json` 尚待選題與核對後建立；不要拿空白檔或未核對的 AI 頁碼當正式測試集。每次 CLI 另存 data/runs/，保留原始結果；每個命令都重新載入，總 elapsed_ms 含載入，不能直接當暖機查詢速度。上述逐方法一次命令只用於檢查評估管線，不等於完成前述正式比較。

歷史原文與逐例輸出留在 data/；共享報告包含方法、識別、題號、彙總、失敗分析與限制，讓他人能審查結論，也不把受限制教材原文公開。
